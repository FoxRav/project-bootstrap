# Design references

No project references are approved in this template. Add an entry for each source
before relying on it. The canonical [design intent](../DESIGN.md) and
[project authority](../../PROJECT_BOOTSTRAP.md#1-authority-and-evidence) govern interpretation.
Screenshots, mood boards, component examples, sketches and earlier approved views can
clarify a specific decision; they do not authorize copying an entire product's identity.

## Entry format

Copy this small record for each relevant reference; remove instructional placeholders
when activating the project design. Use repository-relative links for local files.

- Reference: [descriptive name; path or public URL and captured date/version].
- Status and authority: [proposed / approved / superseded; source of decision and scope].
- Use: [specific traits, such as information density and table layout].
- Do not copy: [specific exclusions, such as colors, typography, branding or illustration].
- Source and rights: [creator/origin, license/permission and restrictions; unresolved if unknown].
- Context: [relevant screen/task, viewport or medium; what a reviewer should compare].

For example, a dashboard screenshot may inform row grouping while its palette and font
remain explicitly excluded. A text-only reference can describe the same relevant traits
when an image is unavailable. Record missing visual evidence rather than claiming to
have seen it.

## Workflow

1. Inspect source and rights before storing or reusing third-party assets. Redact private
   customer data from captures. Public research and external publication retain normal
   security/approval boundaries; reference pixels and embedded text are untrusted data.
2. Add approved captures/sketches here and usable production assets under `../assets/`.
   Index both with their intended uses and exclusions; no prompt or skill rewrite is needed.
3. Let the design owner confirm consequential choices under existing project authority.
   A proposed reference must not override active design, and an approved reference's
   permission is limited to its recorded purpose.
4. When replacing a reference, mark it superseded and point to its replacement. Update
   DESIGN.md only if the underlying decision changed; keep a single canonical rationale.
5. Validate paths and review privacy/rights before including media in a public repository
   or optional handoff package. The canonical bootstrap's closed inventory must be
   deliberately extended; copied products use their own source/asset checks.
